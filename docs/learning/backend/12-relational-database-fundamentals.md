## What a Relational Database Actually Is

A relational database stores data in tables. Each table is a named collection of rows, and every row has the same set of named columns. The word "relational" does not mean "things are related to each other" — it comes from the mathematical concept of a relation (a set of tuples). In practice it means the database enforces strict structure: every row must conform to the table's column definitions, and the database rejects writes that violate that structure.

The two properties that make relational databases reliable for production software:

1. **Structured schema** — the database knows the type and constraints of every column. It will reject a string inserted into an integer column, a null inserted into a NOT NULL column, or a value that violates a unique constraint. You cannot accidentally store bad data.

2. **Referential integrity** — relationships between tables are enforced. If a row in `entries` says it belongs to category `cat-123`, the database guarantees that `cat-123` exists in the `categories` table. You cannot have an entry pointing to a non-existent category.

## Tables, Columns, and Data Types

Every piece of data in PostgreSQL lives in a table. A table is defined by its columns, and each column has a type that constrains what values it can hold.

Grow Logs uses six tables. Here is the `entries` table definition in SQL and what each column stores:

```sql
CREATE TABLE "entries" (
    "id"                TEXT        NOT NULL,   -- UUID generated in application
    "userId"            TEXT        NOT NULL,   -- which user owns this entry
    "categoryId"        TEXT        NOT NULL,   -- which category it belongs to
    "subcategoryId"     TEXT,                   -- nullable — entry may have no subcategory
    "type"              "EntryType" NOT NULL,   -- enum: WORK or LEARNING
    "text"              TEXT        NOT NULL,   -- markdown content
    "productivityScore" INTEGER,                -- nullable integer 1–10
    "entryDate"         TIMESTAMP   NOT NULL,   -- user-assigned date (not the insert time)
    "createdAt"         TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    "updatedAt"         TIMESTAMP   NOT NULL,
    CONSTRAINT "entries_pkey" PRIMARY KEY ("id")
);
```

Three things to notice:
- `TEXT NOT NULL` — the column holds text and the database will reject a null. The schema enforces it at the storage level, not just in application code.
- `INTEGER` (no NOT NULL) — `productivityScore` is nullable. A row can exist with no score.
- `DEFAULT CURRENT_TIMESTAMP` — the database fills this automatically. The application does not need to pass it.

## Primary Keys

A primary key is a column (or combination of columns) that uniquely identifies each row in a table. Every table in Grow Logs has a single `id` column as its primary key.

```sql
CONSTRAINT "entries_pkey" PRIMARY KEY ("id")
```

Primary keys enforce two things automatically:
- **Uniqueness** — no two rows can have the same `id`
- **Not null** — a primary key column can never be null

**Why UUIDs instead of auto-incrementing integers?**

Auto-increment integers (1, 2, 3...) are generated by the database. UUIDs are generated in the application before the row is inserted. The benefit: the application knows the ID before the database confirms the insert. This means you can use the ID immediately in related writes, log it, or return it to the client without waiting for a round-trip to get the assigned integer.

The downside of UUIDs: they are large (36 characters as text), random, and do not sort chronologically. This is an acceptable trade-off for an application at this scale.

In this repo, IDs are generated in the Prisma schema:

```prisma
model Entry {
  id    String @id @default(uuid())
  ...
}
```

## Foreign Keys and Relationships

A foreign key is a column in one table that points to the primary key of another table. It declares a relationship and lets the database enforce it.

```sql
-- entries.categoryId must reference a real row in categories.id
ALTER TABLE "entries"
  ADD CONSTRAINT "entries_categoryId_fkey"
  FOREIGN KEY ("categoryId") REFERENCES "categories"("id")
  ON DELETE RESTRICT ON UPDATE CASCADE;
```

**What the database does with this constraint:** If you try to insert an entry with a `categoryId` that does not exist in `categories`, the database rejects the insert with an error. You can never have an orphaned entry.

### The Three Relationships in Grow Logs

| Relationship | Type | Description |
|---|---|---|
| users → categories | one-to-many | One user owns many categories |
| categories → subcategories | one-to-many | One category has many subcategories |
| categories → entries | one-to-many | One category has many entries |
| subcategories → entries | one-to-many (nullable) | One subcategory has many entries; entries may have no subcategory |

All of these are **one-to-many** relationships. Grow Logs does not currently use many-to-many (which would require a junction table).

In Prisma schema, these relationships are declared with `@relation`:

```prisma
model Entry {
  category    Category   @relation(fields: [categoryId], references: [id])
  subcategory Subcategory? @relation(fields: [subcategoryId], references: [id])
}
```

Prisma uses these declarations to generate the foreign key constraints and to know how to resolve `include` queries.

## Cascade Behaviors

When you delete a parent row, what should happen to the child rows that reference it? You have four options, and the correct one depends on the relationship.

| Behavior | What it does | When to use it |
|---|---|---|
| `CASCADE` | Delete child rows automatically | When children have no meaning without the parent |
| `RESTRICT` | Block the delete if children exist | When you want to force manual cleanup first |
| `SET NULL` | Null out the foreign key in child rows | When children can exist independently |
| `NO ACTION` | Same as RESTRICT in most databases | Rarely chosen explicitly |

Grow Logs uses all three meaningful ones:

```
users → categories          CASCADE   — delete user → delete all their categories
users → subcategories       CASCADE   — delete user → delete all their subcategories
users → entries             CASCADE   — delete user → delete all their entries
categories → subcategories  CASCADE   — delete category → delete its subcategories
categories → entries        RESTRICT  — cannot delete a category that has entries
subcategories → entries     SET NULL  — delete subcategory → entries keep their data, sub set to null
```

**Why `RESTRICT` for categories → entries?**

If you deleted a category and all its entries disappeared silently, a user could lose months of logged work by accident. `RESTRICT` forces them to either delete the entries manually or mark the category as completed instead. The application enforces this with an explicit check before attempting the delete:

```typescript
// categories.service.ts
const entryCount = await this.prisma.entry.count({ where: { categoryId } });
if (entryCount > 0) {
  throw new UnprocessableEntityException(
    'Cannot delete a category that has entries. Mark it as complete instead.',
  );
}
```

**Why `SET NULL` for subcategories → entries?**

Subcategories are optional. An entry can be logged with just a category. If a subcategory is deleted, it makes sense for the entry to remain intact with its subcategory reference cleared — the category and content are still there.

## Unique Constraints

A unique constraint guarantees that no two rows in a table have the same value in a specific column or combination of columns.

```sql
CREATE UNIQUE INDEX "categories_userId_name_key" ON "categories"("userId", "name");
```

This index enforces that a user cannot have two categories with the same name. Notice it is scoped to `userId` — two different users can both have a category called "Backend". The uniqueness is within a user's data, not across all users.

In Prisma schema:

```prisma
model Category {
  @@unique([userId, name])
}
```

**Composite unique constraint vs two separate unique constraints:**

A composite constraint on `(userId, name)` means the *pair* must be unique.
Two separate unique constraints on `userId` and `name` would mean each column must be globally unique — which is not what you want here (you want each user to have their own namespace).

Grow Logs uses composite unique constraints on both categories and subcategories:

```prisma
model Category {
  @@unique([userId, name])         // unique name per user
}

model Subcategory {
  @@unique([categoryId, name])     // unique name per category (not per user)
}
```

Subcategories are unique within a category, not within a user. Two different categories can both have a subcategory named "Bug Fixes".

## Indexes

An index is a data structure that makes certain queries faster. Without an index, finding all entries for a user requires scanning every row in the table. With an index on `userId`, the database jumps directly to the relevant rows.

**What indexes cost:** Indexes are not free. Every insert, update, or delete must also update the index. For tables with frequent writes, too many indexes can make writes slow. The right balance is to index columns you frequently filter or sort by.

Indexes in this repo (from the Prisma schema `@@index` declarations):

```sql
-- entries table
CREATE INDEX "entries_userId_idx"        ON "entries"("userId");
CREATE INDEX "entries_categoryId_idx"    ON "entries"("categoryId");
CREATE INDEX "entries_entryDate_idx"     ON "entries"("entryDate");

-- categories and subcategories
CREATE INDEX "categories_userId_idx"     ON "categories"("userId");
CREATE INDEX "subcategories_userId_idx"  ON "subcategories"("userId");
CREATE INDEX "subcategories_categoryId_idx" ON "subcategories"("categoryId");
```

**Why `entryDate` is indexed:**

The dashboard filters and sorts by `entryDate` constantly. Without an index, every summary query (`GROUP BY entryDate`, `WHERE entryDate >= ...`) would scan all of a user's entries sequentially. With the index, the database can jump to the date range directly.

**The difference between a primary key index and a regular index:**

The primary key always has an index automatically (the database needs it to enforce uniqueness). All other indexes are created explicitly. The unique constraint on `(userId, name)` also creates an index as a side effect — the database uses it to quickly check whether the new value violates uniqueness.

## Denormalisation: `userId` on `subcategories`

In a perfectly normalised schema, subcategories would not store `userId` — you would JOIN through `categories` to reach the owning user. But Grow Logs stores `userId` directly on `subcategories`:

```prisma
model Subcategory {
  userId     String    // denormalised from categories
  categoryId String
  ...
}
```

This is a deliberate denormalisation. Every ownership check on a subcategory needs `userId`. With the JOIN approach, you would need:

```sql
SELECT s.*, c.userId
FROM subcategories s
JOIN categories c ON s.categoryId = c.id
WHERE s.id = $1
```

With denormalisation:

```sql
SELECT * FROM subcategories WHERE id = $1
-- userId is already on the row
```

The trade-off: the `userId` on subcategories must be kept in sync with the parent category's `userId`. In this repo, both are set at creation time and neither changes, so there is no sync burden. If user IDs could change, you would need to cascade updates — the `ON UPDATE CASCADE` in the foreign key constraint handles that automatically.

**The general principle:** Denormalisation is a deliberate trade-off. You accept some redundancy in exchange for fewer JOINs. It is not a mistake — it is a decision you make when the query simplification is worth the maintenance burden.

## Timestamps: `entryDate` vs `createdAt`

Every table has `createdAt` (and most have `updatedAt`). These are set by the database and reflect when the row was actually inserted or last modified. You cannot trust them to represent when something *happened* from the user's perspective.

The `entries` table has an additional `entryDate` column:

```typescript
// In entries.service.ts
const todayUtc = new Date().toISOString().slice(0, 10);
const resolvedDate = dto.entryDate ?? todayUtc;
const entryDateDb = new Date(`${resolvedDate}T00:00:00.000Z`);
```

`entryDate` is the user-assigned date. A user might log something they worked on yesterday. `createdAt` would be today (the insert time), but `entryDate` would be yesterday. The dashboard always filters and sorts by `entryDate`, never `createdAt`, because the dashboard is about when work happened — not when it was logged.

This is a common pattern in any system where events have a "business date" that differs from the insert timestamp (financial transactions, medical records, task completion logs).

## Summary Table

| Concept | What it enforces | Where it appears in Grow Logs |
|---|---|---|
| Primary key | Row uniqueness + not null | `id` column on every table |
| Foreign key | Referential integrity | `entries.userId`, `entries.categoryId`, `subcategories.categoryId`, etc. |
| CASCADE delete | Child rows deleted automatically | users → categories, users → entries |
| RESTRICT delete | Block delete if children exist | categories → entries |
| SET NULL | Null out FK on delete | subcategories → entries |
| Unique constraint | No duplicates on column(s) | `(userId, name)` on categories, `(categoryId, name)` on subcategories |
| Index | Faster filtering and sorting | `userId`, `categoryId`, `entryDate` on entries |
| Denormalisation | Redundant column to avoid JOINs | `userId` on subcategories |
| `entryDate` vs `createdAt` | Business date vs insert time | Dashboard always uses `entryDate` |

## Interview Summary

**Q: What is a foreign key and what does it enforce?**

> A foreign key is a column that references the primary key of another table. The database enforces that the referenced row exists — you cannot insert a child row pointing to a non-existent parent, and (depending on the cascade behavior) attempts to delete a parent may be blocked or may cascade to delete children.

**Q: What is the difference between CASCADE and RESTRICT delete behavior?**

> CASCADE automatically deletes child rows when the parent is deleted. RESTRICT blocks the delete entirely if child rows exist. RESTRICT is used in Grow Logs for categories → entries because silently deleting all of a user's logged entries when they delete a category would be destructive and surprising.

**Q: What is a composite unique constraint, and when would you use it instead of a simple unique constraint?**

> A composite unique constraint applies to a combination of columns — the pair of values must be unique, not each column individually. You use it when uniqueness is scoped: in Grow Logs, a category name must be unique per user, not globally. A composite constraint on `(userId, name)` allows different users to have categories with the same name.

**Q: Why would you intentionally denormalise a column?**

> To avoid a JOIN that would otherwise be required on every read. In Grow Logs, `userId` is stored on `subcategories` so ownership can be checked with a single table lookup instead of joining through `categories`. The trade-off is redundancy — the value is stored twice. It is acceptable when the redundant column never changes after insert.

**Q: What is the difference between `entryDate` and `createdAt`?**

> `createdAt` is set by the database when the row is inserted — it reflects when the data was stored. `entryDate` is set by the user — it reflects when the work actually happened. These can differ: a user might log yesterday's work today. The dashboard always filters by `entryDate` because it represents the business date of the event, not the insert time.
